# AWS services used

| Service | Role in this project | Required? |
|---|---|---|
| **AWS Amplify Hosting** | Builds the site from GitHub on every push, stamps the deploy into the page, and serves it over HTTPS from Amplify's CDN | Yes, the challenge's hosting requirement |
| **AWS Budgets** | A $5/month cost alarm that emails me before anything costs real money | No, but it's a habit worth showing |

Nothing else, on purpose. See [Why there's no backend](#why-theres-no-backend).

## AWS Amplify Hosting

**What it does here**

- **CI/CD from GitHub.** The app is connected to the `main` branch of `github.com/MdIbuA/ibu-receipts`. Each push starts a build: Provision → Build → Deploy.
- **The build spec is in the repo** (`amplify.yml`). The build phase runs one command, `bash scripts/stamp-build.sh`, and publishes only the `site/` folder (`artifacts.baseDirectory: site`). Docs and scripts never reach the public site.
- **Build variables feed the creative feature.** Amplify exposes `AWS_APP_ID`, `AWS_BRANCH`, `AWS_JOB_ID` and `AWS_COMMIT_ID` during the build. The stamp script writes them, plus a timestamp and the site's total size, into `site/feature/receipts/build-info.js`. The footer claim "deployed on AWS Amplify" prints those values as the page's own receipt. The proof of deployment is written by AWS, not typed by me. The same script derives the app's default domain (`https://<branch>.<app-id>.amplifyapp.com`) and writes it into the page's link-preview tags, so a shared link shows the receipt card.
- **Hosting.** Amplify serves the files over HTTPS on the default `main.<app-id>.amplifyapp.com` domain through its managed CDN. No custom domain; the rubric doesn't score one.

**What a judge should look for in the console** (Amplify → `ibu-receipts`)

1. **Overview:** branch `main`, status *Deployed*, the `amplifyapp.com` domain, last deploy time.
2. **Build history:** at least two builds (#1 initial, #2 after the README update), both green. That shows push-to-deploy working.
3. **Build log** (open a build → Build step): the line
   `build-info: deployed=true app=… branch=main job=2 commit=…`
4. **Hosting → Build settings:** the `amplify.yml` from the repo.
5. **Match it to the live page:** open the site, click **deployed on AWS Amplify** in the footer, and compare the build number and commit with steps 2–3. They match because the build wrote them.

**Cost**

Amplify Hosting bills build minutes and data served. This build takes about a minute, and a visitor's first load is about 42 KB over the wire, so a thousand visits move well under 100 MB. At list prices (check the [Amplify pricing page](https://aws.amazon.com/amplify/pricing/)) that's cents per month, and new accounts' free-tier credits cover it.

## AWS Budgets

**What it does here:** a monthly cost budget named `ibu-receipts-guard`, set at $5, with an email alert. Set up before the Amplify app, in DEPLOY.md step 1.

**What to look for:** Billing and Cost Management → Budgets → `ibu-receipts-guard`, with actual spend near $0.

## Why there's no backend

The creative feature only needs data I already have at build time: claims, evidence links, and the deploy's own metadata. A Lambda, an API Gateway or a database would add:

- **failure points during the judging window** (cold starts, throttling, expired credentials),
- **secrets to manage**, and
- **cost and abuse surface** for no visible gain.

The rubric rewards a site that *loads during judging* and AWS usage that's *documented*. So the one dynamic piece, the deploy receipt, is generated by the Amplify build itself, and the site that's served is static.

## Services I considered and didn't use

| Service | Why not |
|---|---|
| Amazon S3 + CloudFront directly | Amplify Hosting already gives a CDN, HTTPS and push-to-deploy with less setup. I used S3 + CloudFront by hand for DocuMind AI. |
| AWS Lambda + Amazon Bedrock (e.g., an "ask about me" bot) | Every portfolio has one; it would cost money per visit and could fail mid-judging. My Bedrock and Lambda work is in the projects instead, each with a receipt. |
| Amazon DynamoDB (e.g., a guestbook) | Needs a write API and moderation, and doesn't reveal anything about me. |
